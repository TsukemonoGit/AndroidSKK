# 実装プラン: `updateSuggestions` コルーチン管理の修正

## 1. 問題の根本原因

### 1.1 Jobチェーンによる即時キャンセル

`SKKEngine.kt` の `updateSuggestions()` は以下のようなコードになっている:

```kotlin
mUpdateSuggestionsJob: Job = Job()  // 初期値: Active

// 呼び出し時に旧Jobをキャンセル
if (!mUpdateSuggestionsJob.isCancelled) {
    mUpdateSuggestionsJob.cancel()       // ← Cancelled に遷移
}
// CancelledなJobを親として新しいJobを作る
mUpdateSuggestionsJob = Job(mUpdateSuggestionsJob)  // ← 子も即時Cancelled
// コルーチン起動 → 即時キャンセルされ、本体が一度も実行されない
launch(context = Dispatchers.Default + mUpdateSuggestionsJob) { ... }
```

**Kotlinコルーチンの仕様:** `Job(parent)` で親Jobを作成した瞬間、親が `Cancelled` 状態であれば子も即座に `Cancelled` に遷移する(`parentCancelled()` が呼び出される)。そのため、2回目以降の `updateSuggestions()` 呼び出しで起動されるコルーチンは本体を一度も実行せず、候補の検索・表示が完全に停止する。

### 1.2 `MainScope()` によるメモリリーク

`updateSuggestions()` と `updateSuggestionsASCII()` の両方で `MainScope().launch(...)` が使用されている。`MainScope()` で作成された `CoroutineScope` は **never cancelled** であり、`SKKEngine` の寿命を超えて生き残る可能性がある。

### 1.3 `invokeOnCompletion` ハンドラ蓄積

`SKKChooseState` 遷移時に `mUpdateSuggestionsJob.invokeOnCompletion { ... }` が呼ばれており、各遷移で新しいハンドラが追加され続ける(蓄積問題)。

---

## 2. 修正方針

**`Job` による親-子チェーン管理を廃止し、`CoroutineScope(SupervisorJob())` による独立したスコープ管理に置き換える。**

### 設計の選択肢比較

| 方式                                    | 長所                                                 | 短所                                     |
| --------------------------------------- | ---------------------------------------------------- | ---------------------------------------- |
| **A: `CoroutineScope + SupervisorJob`** | 単純明快、親子キャンセルの心配なし、メモリリーク解消 | スコープ管理を別途実装する必要あり       |
| B: `Mutex` による直列化                 | 明示的な排他制御                                     | ロジックが複雑化、デッドロックリスク     |
| C: `Channel` + 単一コンシューマ         | 直列化が自動的                                       | 過剰な抽象化、オーバーヘッド             |
| D: `StateFlow` + `collectLatest`        | 関数型、デバウンス容易                               | コード量大きく変更、既存コードとの整合性 |

**→ 方式A(`CoroutineScope + SupervisorJob`)を採用する。**

### 3.3 `updateSuggestions()` の書き換え

**Before:**

```kotlin
internal fun updateSuggestions(str: String) {
    if (mSuggestionsSuspended) return
    if (!mUpdateSuggestionsJob.isCancelled) {
        mUpdateSuggestionsJob.cancel()
    }
    mUpdateSuggestionsJob = Job(mUpdateSuggestionsJob)
    MainScope().launch(context = Dispatchers.Default + mUpdateSuggestionsJob) {
        // 検索本体...
    }
}
```

**After:**

```kotlin
internal fun updateSuggestions(str: String) {
    if (mSuggestionsSuspended) return

    // 実行中の検索があればキャンセル(親-子の連鎖問題が起きない)
    mActiveSearchJob?.cancel()

    // 独立したSupervisorJobを持つスコープ上で起動 → キャンセル伝播の心配なし
    mActiveSearchJob = mSuggestionsScope.launch(Dispatchers.Default) {
        if (isActive.not()) return@launch  // キャンセルされていたら即終了

        val set = mutableSetOf<Pair<String, String>>()

        if (str.isNotEmpty())
            for (dict in mDictList) {
                addFound(this, set, str, dict)
            }
        str.replace(Regex("\\d+(\\.\\d+)?"), "#").let {
            if (it != str)
                for (dict in mDictList) {
                    addFound(this, set, it, dict)
                }
        }

        set.distinctBy { it.second }.let { uniqueSet ->
            mCompletionList = uniqueSet.map { it.first }
            mCandidateList = uniqueSet.map { it.second }
        }

        mCandidateKanjiKey = str
        mCurrentCandidateIndex = 0
        withContext(Dispatchers.Main) {
            if (str == "emoji")
                mService.setCandidates(
                    mCandidateList?.map { removeAnnotation(it) },
                    str,
                    skkPrefs.candidatesEmojiLines
                )
            else
                mService.setCandidates(
                    mCandidateList,
                    str,
                    skkPrefs.candidatesNormalLines
                )
        }
    }
}
```

**ポイント:**

- `mSuggestionsScope` は `SupervisorJob` ベースなので、`mActiveSearchJob?.cancel()` を呼んでもスコープ自体は生き続ける
- 旧検索キャンセル → 新検索起動のサイクルが正しく動作する
- `isActive` チェックでキャンセルされた場合は即座に終了

### 3.4 `updateSuggestionsASCII()` の修正

**Before:**

```kotlin
internal fun updateSuggestionsASCII() {
```

**Before:**

**After:**

```kotlin
internal fun suspendSuggestions() {

    mSuggestionsSuspended = true

    mSuggestionsSuspended = false
}
```

### 3.6 `invokeOnCompletion` 依存の削除(line 328周辺)

**Before:**

```kotlin
mCurrentCandidateIndex = 0

return
```

**After:**
`invokeOnCompletion` を削除し、`updateSuggestions()` コルーチン本体の最終処理として `setCurrentCandidateToComposing()` を配置する、またはコールバックパターンに変更する。

**案A: コルーチン内で完結させる**

```kotlin
// updateSuggestions() 内の withContext(Dispatchers.Main) ブロック終了後に呼び出す
withContext(Dispatchers.Main) {
```

→ **案Aで対応する。** 単純で、`invokeOnCompletion` の蓄積問題も同時に解消できる。

## 7. コードレビュー対応（追加事項）

### 7.1 P1: `setCurrentCandidateToComposing()` の不適切な呼び出し元

#### 問題

`invokeOnCompletion` 依存を解消し `setCurrentCandidateToComposing()` を
`updateSuggestions()` コルーチン内へ移動した結果、**全検索完了時**（かな入力中の
`SKKKanjiState` / `SKKOkuriganaState` / `SKKAbbrevState` など）にも毎回
`setComposingTextSKK(firstCandidate)` が実行されるようになった。

**旧コードでの意図:** `setCurrentCandidateToComposing()` は
`mCurrentCandidateIndex < 0 && SKKChooseState` の**後退遷移パス（back-from-choose）**
でのみ、`invokeOnCompletion` 経由で呼ばれていた。

**リグレーション:** ユーザーが `▽あ` と打鍵中にも関わらず、候補検索の完了ごとに
composing text が `愛` などの第1候補に上書きされる。

#### 修正案

`setCurrentCandidateToComposing()` の呼び出しにガード条件を追加する。
2つの選択肢があり、より保守性の高い **案A** を採用する。

**案A（推奨）: `updateSuggestions()` 内の呼び出し前にガードを追加**

```kotlin
withContext(Dispatchers.Main) {
    if (str == "emoji") {
        mService.setCandidates(
            mCandidateList?.map { removeAnnotation(it) },
            str,
            skkPrefs.candidatesEmojiLines
        )
    } else {
        mService.setCandidates(
            mCandidateList,
            str,
            skkPrefs.candidatesNormalLines
        )
    }
    // 後退遷移時（Choose → Kanji/Abbrev に戻る）のみ composing text に反映
    // 通常のかな入力中（KanjiState/OkuriganaStateなど）は候補表示のみ更新し、
    // composing text は上書きしない
    if (state === SKKChooseState || state === SKKNarrowingState) {
        setCurrentCandidateToComposing()
    }
}
```

**案B: `setCurrentCandidateToComposing()` 内部でガード**

```kotlin
fun setCurrentCandidateToComposing() {
    // 後退遷移時のみ実行（旧コードの意図を維持）
    if (state !== SKKChooseState && state !== SKKNarrowingState) return
    getCandidate(mCurrentCandidateIndex)?.let { candidate ->
        setComposingTextSKK(candidate + mOkurigana)
    }
}
```

→ **案Aを採用する。** ガード条件を呼び出し元に集約することで:

- `setCurrentCandidateToComposing()` のシグネチャ・責任を最小限に保てる
- 将来的に別の呼び出し元が増えた際、呼び出し元で文脈に応じた制御が可能
- `state` の条件が1箇所にまとまり、意図が明確になる

### 7.2 P1: 候補ゼロ時に `IndexOutOfBoundsException` でクラッシュ

#### 問題

`updateSuggestions()` の検索結果がゼロ件のとき:

1. `mCandidateList` は空リスト `[]` になる（`null` ではない）
2. `mCurrentCandidateIndex = 0` が設定される
3. `setCurrentCandidateToComposing()` が呼ばれる
4. `getCandidate(0)` 内で `mCandidateList?.let { it[0] }` が実行される
5. `it` が空リストなので `it[0]` が `IndexOutOfBoundsException` をスロー

修正前は `SKKChooseState` 遷移時のみ呼ばれていたため候補が必ず存在したが、
今回の変更で `updateSuggestions()` の全呼び出しで実行されるようになり、
**辞書にない読みを打つ日常操作でも再現可能な重大なリグレッション**。

#### 修正案

`setCurrentCandidateToComposing()` 内で `mCandidateList` の空リストチェックを行う。
`getCandidate()` も同様のガードを持つが、防御的に `setCurrentCandidateToComposing()`
側にチェックを追加する（呼び出し元の意図を関数内で検証する）。

```kotlin
fun setCurrentCandidateToComposing() {
    // 候補リストが未初期化 または 空リストの場合は何もしない
    val candidates = mCandidateList ?: return
    if (candidates.isEmpty()) return
    if (mCurrentCandidateIndex < 0 || mCurrentCandidateIndex >= candidates.size) return

    getCandidate(mCurrentCandidateIndex)?.let { candidate ->
        setComposingTextSKK(candidate + mOkurigana)
    }
}
```

`getCandidate()` 側にも防御的なチェックを追加（オプションだが推奨）:

```kotlin
private fun getCandidate(index: Int): String? =
    mCandidateList?.let { list ->
        if (index in list.indices) {
            processConcatAndMore(removeAnnotation(list[index]), mCandidateKanjiKey)
        } else {
            null
        }
    }
```
